# Verdandi

Verdandi is a local-first workspace and personal agent platform for coding agents. It drives *harnesses* (Claude Code first, then its own native agent loop, then others) and routes every task to the harness, provider, model and effort level that finishes it at the lowest effective cost. It also remembers, learns skills, runs on schedules and can be reached from chat apps.

The design lives in `docs/DESIGN.md`. Read the section that covers what you're changing before you change it.

**Status:** M1 (core loop) in progress, with much of M2 (routing) and M3 (worktrees, checkpoints, verifiers and escalation, memory, session search) built alongside it. "How it works" below lists what exists; what it doesn't name, such as the gateway's platforms beyond Telegram, doesn't exist yet. Packages are created when their milestone starts (DESIGN.md §20–21), not before.

## What we never compromise on

1. **Size every task correctly.** We optimize cost per *completed* task, not per request. That applies to you too: don't read files you don't need, don't dump huge outputs into context, and pick the smallest check that proves your change.
2. **Don't break the cache.** Within an agent session, the system prompt and tool list never change. Anything that changes between turns goes into the next user turn. Compression is the only allowed cache break.
3. **Local-first and private.** Nothing leaves the machine except calls to providers the user configured.
4. **The user always wins.** Overrides take one click, are recorded, and are never argued with.
5. **Performance.** No continuously repainting animations, small WebSocket payloads, virtualized long lists. Our users drive agents all day, and they notice a dropped frame or a spinner that lies about progress.

## How we build

Fight scope creep. Look for the smallest model of the problem that makes the correct behaviour unsurprising. Measure twice, cut once, and don't build what isn't needed yet.

**Before writing code** (the ponytail ladder), stop at the first rung that holds:

1. Does this need to exist at all?
2. Does it already exist in this codebase?
3. Do the standard library or Bun do it?
4. Does a native platform feature cover it?
5. Does an installed dependency solve it?
6. Can it be one line?
7. Only then: the minimum code that works.

Read the task and trace the real flow *before* climbing the ladder. Fix bugs at the root cause: grep every caller and fix the shared function once. Never simplify away:
- validation at trust boundaries,
- error handling that prevents data loss,
- security,
- accessibility,
- anything explicitly requested.

Non-trivial logic leaves one runnable check behind. Mark deliberate corner-cutting with a `ponytail: <ceiling>, <upgrade path>` comment. The full rules are in the `ponytail` skill, and `ponytail-review` reviews a diff for over-engineering.

**Adding a capability** (the Footprint Ladder): try each step in order before moving to the next:
1. extend existing code;
2. a CLI command plus a skill;
3. a tool that is only enabled under certain conditions;
4. a plugin;
5. an MCP server;
6. a new core feature, as the last resort.

These are good defaults, not laws. The developer's preferences override anything here. If a rule fights the task in front of you, say so plainly and get a human sign-off before breaking it.

## Glossary

- **you:** the agent reading this file and changing Verdandi.
- **we / maintainers:** the people building Verdandi, i.e. the people you're talking to.
- **user:** a person using Verdandi to direct agents.
- **agent:** an AI agent running inside Verdandi. Depending on context, this can include you.
- **harness:** whatever runs the agent loop (Claude Code, the native harness, Codex, …).
- **provider:** where inference runs (Anthropic API, OpenRouter, Ollama, …).
- **access mode:** `subscription`, `metered` or `local`.
- **target:** a harness, provider, model and access mode together.
- **route:** a target plus effort level, interaction mode and subagent profiles.
- **task:** a run of turns under one route. The unit of routing.
- **thread:** a durable conversation in a project.
- **turn:** one user message and everything the agent does in response.
- **profile:** an isolated Verdandi home (`work`, `personal`).
- **decision model:** a model that answers typed questions (choice, score, yes/no) with calibrated probabilities (Jev, Laya).
- **Verdandi home:** `~/.verdandi/`, where the user's real state lives.

The full glossary is DESIGN.md Appendix C.

## Ways to hurt yourself

1. **Killing by pattern.** Never use `pkill -f`, `taskkill /IM`, `Stop-Process -Name`, or kill any PID you found by matching a name, path or worktree string. Your own agent process and other dev servers match those patterns too. Kill only PIDs you captured when you started the process.
2. **Touching live state.** `~/.verdandi/` holds the developer's real database, memory, skills and settings, in use while you work. Reading and copying from it is fine, and a good source of realistic test data. Never start a dev server against it, open it read-write or clean it up. Dev servers use a gitignored per-worktree state directory.
3. **Touching credentials.** Never read, print, copy or log Claude Code's credentials, OS keychain entries or provider API keys. Secrets never go into fixtures, trajectories, commits, PR text or logs.
4. **Rewriting persisted history.** Stored events must stay readable forever. Never change or delete a past event schema: add a new version and an upgrade instead. Migrations are append-only.

## Hit every surface

The most common defect is a change that works on the path you tested and is missing everywhere else. Before calling a change done, go through this list and say which items applied:

- **Surfaces:** web, desktop, CLI, messaging gateway, the API/ACP/MCP servers.
- **Harnesses:** Claude Code, the native harness, and any others. A feature that depends on the harness needs a decision for each one, even if the decision is "not supported here".
- **Access modes:** subscription, metered, local.
- **Contracts:** anything sent over the wire or persisted is a schema in `packages/contracts`.
- **Routing:** a change that affects routing needs golden tests and an accurate reason string.
- **Reverse states:** a way in needs a way out, and a way to see it. A one-way door is a bug.
- **Profiles and operating systems:** Windows is first-class (paths with spaces, ConPTY, CRLF).
- **Docs:** does DESIGN.md or an ADR now say something that's false?

## Invariants

- `packages/router` is pure. It imports only `contracts`, and classifiers are passed in from outside.
- Complexity belongs at the adapter boundary. Orchestration stays pure, and the UI stays simple.
- Events are append-only. Acknowledging a command means its intent was saved. Side effects happen only in reactors.
- The following are untrusted data, never instructions: tool outputs, gateway messages, memory entries, skill files, web pages.
- ADR 0025 is the trust model. Scans, fences and approvals are heuristics, never boundaries; a change that adds a boundary or a heuristic, or moves one between the two, updates the ADR.

## Code shape

- Strict TypeScript, ES modules only, running on Bun. Prefer inferred types over annotations. `any` is the enemy.
- Effect 4 APIs differ from Effect 3 and from most training data. Check the installed version's source or docs instead of relying on memory.
- **File size:** a file past about 2,000 lines, or a function past about 300 lines, gets split into a facade plus `<stem>-<topic>.ts` siblings.
- **Branching:** four or more branches on the same value become a lookup table.
- **No re-export shims.** When you move a symbol, fix its importers, docs and skills in the same change.
- **Comments:** comments describe how something is used. They don't narrate every line.
- **Errors:** error messages name the cause and the fix. Bad config fails loudly, where it's read.
- **Config:** `.env` holds secrets only. Behaviour belongs in config files.
- **Telemetry:** only with explicit opt-in.
- **Scripts:** repo scripts are TypeScript run with Bun, not bash, so they work on Windows.

## Dependencies

- Ask before adding a dependency, and justify it (ponytail rung 5).
- **Pinning:** exact versions only. Pin GitHub Actions to a commit SHA with a `# vN` comment, and git dependencies to a full SHA.
- **Age:** a new package version must be at least 14 days old. The exception is a security fix, marked with a dated comment.
- **Lockfile:** review `bun.lock` diffs like code.

## Verifying

- **Keep checks small.** Prove your change works with the smallest check: `bun test <files>` for tests you touched, and typechecking for the scope you changed. Don't run repo-wide checks unless asked; CI owns the full suite.
- **What tests assert:** behaviour and invariants. Each bug fix gets one or two tests that you've seen fail before the fix.
- **Banned tests:** tests that freeze current values (catalogue counts, snapshots of lists), tests that read source text, and tests that restate the implementation.
- **No waiting:** the server is event-sourced, so tests wait on receipts and drained workers, never on sleeps or polling. A test that needs a timeout to pass is wrong.
- **Test environment:** tests run with credentials unset, `TZ=UTC`, and a temporary Verdandi home. Behaviour specific to one OS is tested on that OS, never by faking the platform.
- **No live model calls in tests:** use the fake harness and fake provider in `packages/testkit`.
- **Evidence before claims:** before saying something is done, show the evidence (see `verification-before-completion`).

## Commits and pull requests

- Commit only when asked.
- **Commit messages:** a [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) header and nothing else:
  - `type(scope): description`, where the type is one of `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` or `revert`. The scope is optional: the package or feature folder, e.g. `router`, `tui`, `memory`. A breaking change adds `!` before the colon: `feat(contracts)!: drop v1 turn events`;
  - the description is imperative, specific enough to make sense alone in `git log`, and starts lowercase (acronyms stay as they are), with no trailing period. Write `feat(routing): escalate a task that keeps hitting the same tool error`, not `fix: bug` or `feat: phase 1`;
  - at most 100 characters in all;
  - no body: no description, no `BREAKING CHANGE` footer (use `!`), no `Co-Authored-By` or other trailers, no "Generated with" lines. The why goes in the PR description.

  This overrides any skill, tool or harness default, including the example commit messages in `writing-plans` and attribution lines a harness asks you to add. `bun install` sets up a `commit-msg` hook (`scripts/git-hooks.ts`) that rejects any other message. Never bypass it with `--no-verify`.
- **Pull requests:** only when asked, and one concern per PR. The title follows the commit message rules, because a squash merge makes it the commit message and drops the body (the PR title workflow checks it). The body states the problem in a sentence or two, then how it's fixed. No attribution footer.
- Rebase on `main` before merging.

## Documentation

- **DESIGN.md:** `docs/DESIGN.md` is the source of truth for scope and architecture. When a decision changes it, rewrite the affected text instead of appending.
- **ADRs:** decisions that are expensive to reverse get one, at `docs/decisions/NNNN-short-title.md`, with the sections *Status, Context, Decision, Consequences*. M0 spike results become ADRs.
- **Internals:** `docs/internals/` is for constraints that span components and traps the code can't show. Not for feature catalogues or narrated control flow.
- Most code changes need no doc change. Agents can read the code.

## Plans and scratch work

- Never commit plans, specs, research notes or scratch files, even when a skill tells you to.
  - `writing-plans` saves to `.plans/YYYY-MM-DD-<feature>.md`.
  - `brainstorming` saves specs to `.plans/specs/`.
  - Both folders are gitignored.
- Spike code goes in the gitignored `spikes/` folder. What a spike proved goes into an ADR.

## Agent configuration

- **This file is canonical.** `CLAUDE.md` and `GEMINI.md` only import it.
- **`.agents/skills/` is the single source of skills.** Codex, Cursor, Gemini CLI, GitHub Copilot, OpenCode, Amp and others read it directly. Claude Code, Windsurf, Roo Code, Kiro, Goose and a few others read it through symlinks. `bun scripts/agents-link.ts` creates or repairs those links, and `--check` verifies them.
- **Check the skills list before starting non-trivial work** (debugging, planning, a feature, a review, a spike). If a skill fits, use it. Trivial requests don't need a skill check.
- **Edit skills only in `.agents/skills/`,** never through a link. A skill's folder name must equal its `name`, and its description says what it does and when to use it (see `writing-skills`).
- **Vendored skills stay byte-identical to upstream** (sources in `.agents/README.md`). Put Verdandi-specific overrides in this file instead. A reference like `superpowers:<name>` means the `<name>` skill in `.agents/skills/`.
- **Area files:** when a directory develops its own conventions, give it an `AGENTS.md` (aim for under about 8k characters) and add it to this table:

| Working in | Read |

| `apps/agent/src/event-store/` | [`apps/agent/src/event-store/AGENTS.md`](apps/agent/src/event-store/AGENTS.md) |

## How it works

What runs today (M1, in progress):

- **Running it:** bare `verdandi` (the same as `verdandi chat`) is the terminal chat and the default surface: in a terminal, the terminal UI on OpenTUI (`src/tui/tui.tsx`, ADR 0027); with `--plain`, or when stdin or stdout isn't a terminal, the line chat. Both drive one session (`src/cli/chat-session.ts`: the feed's lines, slash commands, requests, steering, Ctrl+C) through an `Io`, so they can't drift apart; the TUI only draws it, re-rendering at most once per ~16 ms frame, and is imported only when it opens. It connects to the profile's verdandid, or, when none runs (`runningServer`: no `server.json`, or one whose process is gone), starts one in its own process (`serve` in `src/main.ts`, logging warnings only, to stderr) and stops it when you quit; `verdandi run` does the same for one run. `verdandi start` keeps one running for the web UI and, later, the scheduler and gateway. The agent serves no web page (ADR 0026). `verdandi help` prints the usage.
- **Slash commands:** defined once in `packages/contracts/src/slash.ts` (`slashCommands`): each one's arguments (with the choices completion offers), help line, surfaces (`chat`, `web`, `gateway`), whether only the owner may use it in a chat app, the client commands it dispatches, and what it does while a turn runs (`run` at once, `queue` for the next turn, or `refuse` with the reason, which the decider agrees with). `verdandi chat` handles them through a `Record` keyed by the chat's names (so a missing handler fails typecheck); a slash command never answers a waiting request, so `/diff` works while an approval waits. The terminal UI completes them on Tab with a hint under the transcript, `--plain` in a terminal through readline's completer, and `/help` lists them. The web composer offers its commands (mode switches, `/rate`, `/forget-routing`, `/undo-revert`) in the menu that offers `@name` pins and runs them without sending a turn.
- **Workspace:** the profile's `<home>/workspace` (`src/home/workspace.ts`), made a git repo when verdandid starts, is where threads that aren't about one project run; it's stored as a project like any other. `verdandi` and `verdandi run` pick the current folder when it's inside a git repo or has a CLI thread (`cli-threads.json`), else the workspace; `--here` and `--workspace` pick outright. `ProjectsSubscribe`'s snapshot carries its path, and the web's New thread offers it. The home's `workspace.yaml` lists `folders` the agent may also work in (e.g. `~/Downloads`), read when verdandid starts (a broken file stops it, naming the file and key): Claude Code gets them as `additionalDirectories`, fixed at spawn; the native harness's file tools reach them as they do the thread's folder; a confined gateway thread gets neither (see Gateway conversations). Files outside a thread's folder have no checkpoints.
- **Commands and events:** clients send typed RPC (`packages/contracts/src/rpc.ts`) over a WebSocket on `127.0.0.1`, authenticated with the token in the profile's `server.json`. verdandid listens only there and serves no web page: an upgrade that carries any `Origin` is refused before the token is read, since browsers reach it only through `verdandi web`; the CLI and that relay send none. `CommandDispatch` hands a command to the engine, a pure *decider* turns it into *events*, and *projectors* update the read models in the same SQLite transaction. The receipt returns once that transaction commits.
- **Side effects:** after a commit, *reactors* run the side effects. Today they run a harness turn on `turn.started` and report what the harness does back as `harness.report` commands, pass the turn the user's `turn.steered` messages, pass `approval.resolved` answers back to the harness, stop a turn the user interrupted, run a turn's verifiers before it completes, and record each completed turn's trajectory and its task's outcome.
- **Approvals:** a harness that needs the user raises `approval.requested` or `user-input.requested`. It shows in `ThreadView.pendingRequests` until a client answers with `approval.respond`. A turn that ends first, including one cut off by a restart, denies its open requests and records why.
- **Smart approvals:** off unless the home's `approvals.yaml` sets `smart: true` (read when verdandid starts; a broken file stops it, naming the file and key). Then the reactor passes the native harness a `guard` (DESIGN §17): for each `terminal` command, the hard rules (`src/approvals/smart-approvals.ts`: destructive patterns, shell and interpreter wrappers, syntax the guard can't be shown) send it to the user; otherwise the decision layer's `terminal.guard` question (`guardQuestion`, `guardRules` in `packages/decisions`) rates the command without the comments its shell skips, fenced as data, and `approval.guard` logs the answer as `decision.recorded`. A sure `allow` runs it unasked and a `deny` refuses it with its reason, each an `approval.auto` item on the turn; anything else, an error or a 10-second timeout asks the user, with the reason as the request's `note`. On `rules`, only a closed list of read-only commands inside the project passes. The third terminal command in a row a turn doesn't run gets tool-result text telling the agent to stop trying variations. `ApprovalsGet` says whether they're enabled and on; the web composer shows it with Turn off and Turn back on, and `verdandi chat` in its banner with `/smart off|on`, each `approvals.smart.set` → `approvals.smart.changed` on the profile, read at each command. Claude Code keeps its own permission settings; the fake harness has no terminal.
- **Trust:** a project's own commands, its verifiers, worktree setup and MCP servers, run only once the user trusts that exact list in the project (DESIGN §17). Before running an untrusted list, the reactor sends `commands.trust.request`, and the decider records `commands.trust.requested` (the commands and their hash, `src/trust/trust.ts`), a pending request on the running turn that the turn waits on. Allowing it records `commands.trusted` (kept in `trusted_commands`) and runs them; denying it runs nothing, and for verifiers or MCP servers adds a `notice` item saying so, so the task records no verifier run. A list that changed, such as one the turn's agent rewrote, has a new hash and asks again. Verifiers a caller supplies in-process, a batch task's `verify`, aren't the project's and run unasked; a batch denies every trust request, even with `--approve`. Context files go through the same flow (purpose `context`): before each turn the reactor scans the files the turn's harness loads by itself (`HarnessAdapter.loads`; Claude Code: `packages/harness-claude-code/src/context-files.ts`, its CLAUDE.md files up the tree, or AGENTS.md without one, with their `@` imports, and the repo's `.claude` rules, skills, commands and agents, each additional directory's `.claude` skills, commands and agents, its CLAUDE.md files only under `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD`, and the profile's plugin; fake: its folder's `CLAUDE.md`) with the injection question, cached per content (`src/trust/context.ts`). A flagged file whose path and content hash the user hasn't trusted is recorded as `injection.flagged` (`source: "context"`, its `file`) and holds the turn on a trust request; allowing it starts the harness and trusts those contents in the project, and denying it ends the turn naming the files, without starting the harness. `TrustedCommandsList` lists them; the projects page's Trusted project commands and `verdandi chat`'s `/trusted` and `/untrust <n>` show and revoke them (`commands.trust.revoke` → `commands.trust.revoked`).
- **Steering:** `turn.steer` on the running turn records a `user.steer` item and reaches the agent at its next step (Claude Code: the next tool boundary, ADR 0003). The turn stays open until the agent has answered it. Once its agent has finished and its verifiers are about to run (`verifiers.started`), the turn is closed to steers: `turn.steer` is rejected (`TurnVerifying`), telling the user to send a new turn once they finish, and the web composer keeps the text.
- **Modes:** `turn.send` carries an interaction mode, `ask`, `plan` or `build`. It is recorded on the turn, and the harness applies it before the turn's prompt, so the cache survives (Claude Code: `setPermissionMode`; ask and plan both run in its read-only plan mode, build in the user's own default mode). A plan the agent proposes is a `plan.requested`: a `plan` item plus a pending request. Allowing it lets the turn go on building; denying it with `feedback` keeps the agent planning with that feedback (ADR 0003). Allowing it with `plan`, the user's edit (the web card's Edit, `e` in `verdandi chat` through `$VISUAL`/`$EDITOR`), makes the agent build from the edit (Claude Code: `ExitPlanMode`'s `updatedInput.plan`, ADR 0003; fake: echoes it); an empty edit is refused and an unchanged one is a plain approval. The `plan` item keeps both (`edited`), shown as a diff, and an edit counts as a correction, like a rejected plan.
- **Attachments:** `turn.send` can carry images and files. verdandid checks them at the RPC boundary (at most 10 per turn, 5 MB each and 10 MB together, and an image's bytes must match its type: PNG, JPEG, GIF or WebP; anything else, SVG included, is a file) and stores them content-addressed in the profile's `attachments` folder, before the engine accepts the turn. From then on the command, `turn.started` v2 and the feeds carry references (`AttachmentRef`), never bytes. Their contents are untrusted data. The reactor hands the harness each one's path (Claude Code: images as image blocks in the turn's message, files as paths in its text, marked as data, with the folder in `additionalDirectories`; fake: echoes them). An attached image is a routing signal: only catalog targets with `vision` stay candidates. The web composer takes paste, drop and an Attach picker, and a turn shows its thumbnails, fetched from `GET /attachments/<id>` with the page's token in an `Authorization` header, which the web server swaps for the agent's. `verdandi chat` has `/attach <path>` and `/detach`. When verdandid starts and once a day, a background sweep (`AttachmentSweepLive`) deletes the files in `attachments` that no stored turn references and that are over an hour old, such as a rejected turn's; sending the same bytes again makes a file new, so the sweep never races a turn's commit, and a file it can't delete is logged and tried next time. `verdandi doctor` shows the folder's size and how many files no turn references.
- **Verifiers:** a project's `escalation.verifiers` in `.verdandi/routing.yaml` (e.g. `[bun test, bun run typecheck]`) run when a turn's agent finishes successfully after changing files in the project by any means, the same for every harness: the turn's start checkpoint against the folder's tree once its agent is done, untracked files counted and ignored ones not (a folder outside git, which has no checkpoints, counts the agent's file-tool calls), once the user trusts them (see Trust). The reactor runs them in order in the project folder through the platform shell (`/bin/sh -c`, or `cmd /d /s /c`), with no input and a 10-minute limit each, until one fails, before it reports the turn finished, so the thread stays busy and an interrupt kills them and what they started. Each run is a `verifier.ran` event (command, pass, exit code, time, the tail of its output, which is untrusted data), shown as a `verifier` item of the turn in the web UI and `verdandi chat`. A task whose last verifier run failed has outcome status `failed`, and its `verifierRuns` list them.
- **Escalation:** when a verifier fails on a routed task, or else its agent called `report_blocked` during the turn, or else the same tool error (paths, numbers and ids stripped) has come back `escalation.repeatedErrors` times (default 3, 0 never) across the task's turns since it last escalated, the reactor asks with `task.escalate` once the turn ends, one trigger per turn end, and the decider takes the next step of the policy's `escalation.ladder` (default `effort`, `model`, `ask`; `packages/router`'s `escalate`), at most `maxAutoEscalations` (default 1) per task. A step commits `task.escalated` (the trigger, the route before and after, and a reason naming the trigger) and a `turn.started` Verdandi sends, which hands the agent the verifier's output, its own blocked reason or the repeated error, fenced and marked as data. The engine first asks the decision layer whether that text is an injection (`handedText` in the decider); a flagged one still goes over, fenced, under a warning, and the failed turn records `injection.flagged`, shown as an `injection` item in the web UI and a line in `verdandi chat`. The task goes on at the new route on the same harness and session (ADR 0018). Past the limit, with a spend cap reached when the next step would spend metered dollars, or with a broken policy, the step is `ask`, which moves nothing. Pinned threads and tasks pinned with `@name` never escalate, and nothing escalates once another turn has started. The failed turn shows an `escalation` item, the web UI labels the follow-up turn as Verdandi's, and `verdandi chat` prints a line. A turn the decision layer reads as correcting the agent escalates its routed task the same way, one step before it runs (trigger `correction`), with no turn of Verdandi's, no text handed over and no `ask`, and before any de-escalation (DESIGN §8.7); a revert only counts in routing memory. Denying a routed task's plan (an edit isn't a denial) does the same inside the running turn (trigger `plan-rejected`): `task.escalated` carries the plan's `requestId` and is committed right before the denial, so the reactor calls the harness's `reroute` and the agent plans again on the stronger route, an effort step included (ADR 0018); past the limit the denial goes back as it is. The web plan card shows the step, `verdandi chat` prints it, and `verdandi run --deny-requests` follows the turn on. The web route chip's Undo escalation picks the route it escalated from, which pins the thread like any route pick, and `verdandi chat` prints the flags that do the same. The outcome counts `escalations` and lists each trigger that fired with its step (`triggers`), and routing memory counts an escalated task against the route it started on.
- **De-escalation:** when a routed task's latest turn passed all its verifiers, the engine asks the decision layer for the next turn's class too. Mechanical work (`chore.git`, `code.edit.mechanical`, `docs.write`) is routed through `packages/router`'s `deescalate`. It moves the task only to a less capable model on its harness, only when the switch-cost gate lets the warm session go, and never by effort alone. A move commits `task.deescalated` before the turn's `turn.started`. The task stays one task and the thread stays routed, and the move is kept in `ThreadView.routeChanges` as `by: "router"` with its reason. The web UI shows it between the turns, and `verdandi chat` prints a line. Pinned threads and `@name` tasks never de-escalate. Untrusted input: once a turn calls a network tool (`WebFetch`, `WebSearch`, and the native harness's `web_fetch`/`web_search`) or gets text flagged as an injection (`untrustedSource` in `src/routing/untrusted.ts`, the one closed list), the projector keeps it as the turn's `untrusted`, and the warm session holds it from then on (`sessionUntrusted`, read in `loadDeciderState`). While it does, and its harness's sessions can write files or run commands (every harness's can), no route that keeps the session (de-escalation, a plan's build, a new task on its harness) goes below the policy's `untrusted` floor (built in: `minTier: M`, `forbid: [local]`; it adds up across layers, so a project can raise it but not lower it), and the reason names the source and turn. `task.started` records it in `inputs.untrusted`.
- **Interrupting:** `turn.interrupt` ends the running turn as `interrupted` at once, denying its open requests. The reactor then interrupts the turn's fiber, and the thread's next turn waits for the harness to wind down and continues the same session (Claude Code: resumed by id in a fresh process).
- **Feeds:** `ThreadSubscribe` streams a snapshot of the thread, then its events and unstored text deltas. `ProjectsSubscribe` streams every project, a small summary of each thread (title from its first turn, busy, last activity, route, and its cost with metered and subscription dollars kept apart), and each harness's latest subscription window, then a thread's summary again whenever it is created, archived or unarchived, or a turn starts or ends, and a window again whenever the harness reports it changed; the web sidebar and `verdandi chat --list` show both. Clients end a feed with `Unsubscribe` (ADR 0008).
- **Archiving:** `thread.archive` records `thread.archived`, which hides a thread without deleting anything; `thread.unarchive` brings it back. - **Provider health:** a harness reports a request that still failed once its provider's SDK stopped retrying as `provider.failed` (native only: Claude Code's models share one subscription window), with a reason from contracts' closed set (`rate_limit`, `overloaded`, `server_error`, `timeout`, `model_not_found`, `auth`, `billing`, `context_overflow`), the model when the provider's limits are per model (Anthropic's 429 and 529), and `until`: the provider's reset, else a cooldown per reason (`failureCooldownMs`). While a cap over the thread is reached, a turn that would spend metered dollars (on a metered target, or on a harness whose latest quota window runs on extra usage and hasn't reset) is rejected (`SpendCapReached`) naming the cap, the spend and how to raise it; subscription and local turns go on. - **Task limits:** a class's route (or `fallback`, for classes that set none) in the routing policy can set `maxCost` and `maxTurns`; the router copies them into the decision's `limits`, pinned tasks included. The reactor passes them to the harness with what the task has spent so far: its dollars, and its model calls, which a harness reports as it makes each (`model.called`, recorded as `turn.model.called` only for a task with `maxTurns`), so an interrupt or a new process doesn't start the count over (Claude Code: `maxBudgetUsd` and `maxTurns` with what's left, in a process opened for the task, since both are set at spawn). A turn a guard stops ends with status `limit`, which ends the task; its outcome keeps status `limit`.
- **Tasks:** a thread's first turn starts a task (`task.started`, named after that turn), and so does the first turn after a route change or unpin. On each turn end and route change the reactor rebuilds the thread's `TaskOutcome`s from its events into `task_outcomes`: status from the task's last turn, usage by model, running time, and a route change as the user's override. `TaskCostsList` (and `verdandi costs`) sums them into cost per completed task by route, failed tasks' cost included. Trajectories carry their task's id. `task.rate` (the thumbs under a task's last turn in the web UI, `/rate up|down|clear` in `verdandi chat`) records `task.rated`: the outcome keeps the latest `rating`, `null` clears it, and routing memory counts a task rated down as one that didn't succeed.

A session idle past the cache's 5-minute TTL is pruned before its next request even below the trigger. A request the SDK gave up on is classified (`src/provider-failure.ts`) and reported as `provider.failed`, which waits for Verdandi like an approval (see Provider health). An interrupt aborts the request in flight and commits nothing more, and a tool call it left unanswered gets an error result when the next request is built. A new session's system prompt (`src/prompt.ts`, `src/context.ts`) holds the instructions and the skills index (the profile's and extra folders' skills, sorted, within a budget), then the folder's first context file (`AGENTS.md`, `CLAUDE.md`, `.cursorrules`; one, capped), cached up to there, then the folder; each is scanned through the turn's `scan` (the reactor's, recording a hit as `withheld`), and a flagged file becomes a `[BLOCKED: …]` marker and a flagged description is left out, each with a `notice`. The transcript's header keeps it, so a resume builds the same bytes after a file changes. The child starts from the parent's system prompt and tools, less `report_blocked` and, at the policy's `delegation.maxDepth` (default 1), `delegate_task`; it works read-only for a profile or while the parent is in `ask` or planning. Its steps carry the call's `parentToolUseId`, its requests surface on the parent's turn, an interrupt stops it with the parent, its usage counts on the parent's task by model and against its `maxCost`, and its last reply is the call's result. A reply's consecutive `delegate_task` calls run at once, at most `delegation.maxConcurrent` (default 3). The web UI shows the route under the call, and `verdandi chat` and `verdandi run` (on stderr) print a line. Claude Code has its own Task subagents, routed through `route.subagents` (ADR 0014); the fake harness doesn't delegate. MCP (ADR 0031): a new session connects to the servers in the home's `mcp.yaml` and the folder's `.verdandi/mcp.yaml` (`servers: { <name>: { command, args, env, ask, tools: { <tool>: { ask } } } }`, `${VAR}`s filled in from verdandid's environment without its secrets), and with `importClaudeCode: true` in the home's file also the folder's `.mcp.json` and the `mcpServers` key of Claude Code's `~/.claude.json`, which always ask; Verdandi's files win a name clash, the project's over the home's. A project's own servers start only once the user trusts that list (purpose `mcp`, see Trust). A delegated child shares its parent's. Each call asks unless the config marks the tool or server `ask: false` (always in ask and plan mode), and its result's text goes through the reactor's `screen` (source `mcp`), capped at 100,000 characters. Servers stop with the session (`close`), their trees killed by the PID captured at spawn. Tool search (`src/tool-search.ts`): once a new session has 10 or more MCP tools, or 40,000 characters of their definitions, they're deferred, fixed in the transcript's header: by default sent with `defer_loading` after the API's `tool_search_tool_bm25`; with the adapter's `toolSearch: "bridge"` (for providers without server-side search) left out of the request (the header's `deferred`) behind `tool_search` (screened matches), `tool_describe` and `tool_call`, which runs as the real tool, so its `tool.call` item, approval and errors carry the real name. `pause_turn` sends the conversation again. - **Routing:** a thread created without a route is unpinned: when `turn.send` starts a task, the engine loads the project's policy (built-in, plus `.verdandi/routing.yaml` read on each new task) and the decider asks `packages/router` for a `RouteDecision` over the targets whose harness is running. `task.started` carries the decision and its route, which the thread runs on from that turn, applied before its prompt; the projector keeps each in `route_decisions`. A route the user picks (`thread.create` with a route, `thread.route.set` from `verdandi chat` flags or the web route chip, which lists `ModelsList` by harness with the current route marked) pins the thread: its tasks skip the router, and a pick during a routed task is recorded as the override on that task's outcome. `thread.route.unpin` (`verdandi chat --auto`, the chip's Let the router pick) hands it back from the next task. An unknown name, or nothing after it, rejects the turn (`InvalidPin`) naming the valid ones. `thread.budget.set` (`verdandi chat --budget`, the composer's Budget switch) sets the thread's budget mode in place of the policy's `mode`, or clears it with `null`; on an unpinned thread it ends the task, so the next turn starts one routed under it. Approving it commits `task.rerouted` before the approval, and the reactor calls the harness's `reroute` so the rest of the turn runs there (Claude Code: `setModel` inside the turn, ADR 0013). A class's `subagents` in the policy route its `explorer` and `reviewer` subagents; the route carries them, and a harness session keeps the ones it started with (Claude Code: the `agents` option at spawn, ADR 0014; native: a `delegate_task` call that names the profile). `RoutingExplain` returns a task's decision and trace, and `RoutingSimulate` what the router would pick for a draft, which the web composer shows while you type. - **Headless runs:** `verdandi run "<task>"` (`src/cli/run.ts`) sends one turn with nobody at the keyboard: on a new thread in `--project` (default: the current folder), in a worktree of its own with `--worktree` (refused for the workspace), or on `--thread`, in `--mode`, with `--route` pinning the thread (`harness/model/effort`) or handing it to the router (`auto`). ## Where code lives

- **Now:**
  - `apps/agent`: the agent, verdandid and the `verdandi` CLI in one binary (`start`, `web`, `chat`, `run`, `schedule`, `doctor`, `gc`, `devices`, `gateway`, `costs`, `routing`, `decisions`, `batch`, `search`, `skills`, `trajectories`, `key`); `src/batch` runs eval sets. `src` has a folder per feature (`routing`, `decisions`, `memory`, `skills`, `review`, `handoff`, `spend`, `tasks`, `search`, `worktrees`, `checkpoints`, `diffs`, `terminals`, `attachments`, `verifiers`, `gc`, `batch`, `schedule`, `projects`, `home`, `native`, `devices`, `gateway`, `compression`), each holding its logic, tests and CLI command (`*-cli.ts`). `src/event-store` holds the decider, projector, engine, reactor, SQLite and migrations; `src/rpc` the WebSocket API; `src/cli` `verdandi chat` (its session, and the `--plain` line chat), `run`, `web` and `doctor`; `src/tui` the terminal UI;
  - `apps/web`: `verdandi web`'s host: the page (`index.html`, `src/main.tsx`), the server that relays to the agent (`src/serve.ts`) and the LAN gate (`src/lan-gate.ts`);
  - `packages/ui`: the whole UI (React), for every host. `src/state.ts` folds feed messages into what the page shows, `src/client.ts` is the RPC connection, `src/ui` holds shared widgets, and each feature (`threads`, `composer`, `routing`, `spend`, `diffs`, `memory`, `terminals`, `worktrees`) has its own folder;
  - `packages/contracts`: every schema sent over the wire or persisted (commands, events, RPC, harness contract, routes);
  - `packages/harness-claude-code`: the Claude Code adapter and event normalization. `src/smoke.ts` is a manual live check, never run in tests;
  - `packages/harness-native`: Verdandi's own agent loop on the Anthropic API, its model catalog and where its key comes from;
  - `packages/trajectories`: builds a turn's trajectory and each task's outcome from events, redacts secrets, and turns trajectories into chat conversations for export; the reactor saves them to `trajectories` and `task_outcomes` (DESIGN §8.8, §14.6);
  - `packages/router`: the pure routing engine; `src/catalog.json` and `src/policy.json` are its data;
  - `packages/decisions`: the decision layer's `Decide` service and its `rules` backend (DESIGN §9.8);
  - `packages/tools`: Verdandi's own tools, defined once for every harness (DESIGN §9.6);
  - `packages/video`: the video maker: in-page runtime, render engine, lint and check, project templates (DESIGN §24);
  - `packages/testkit`: the fake harness, the fake Anthropic API (`makeFakeAnthropic`, scripted streamed replies through an injected `fetch`), a fake MCP server (`fakeMcpServer`, a stdio script), a fake chat app (`makeFakeChannel`) and temporary Verdandi homes for tests;
  - `docs/`: design and decisions;
  - `.agents/`: agent configuration and skills;
  - `scripts/`: repo tooling.
- **Planned (DESIGN.md §20):**
  - `apps/desktop`: an Electron host that renders `packages/ui` and runs the agent binary or connects to a remote agent (DESIGN §11), so UI changes go in `packages/ui` only;
  - more `packages/harness-*`, `packages/models`, `packages/memory`, `packages/skills`;
  - `plugins/`;
  - `lab/` (Python, offline).
