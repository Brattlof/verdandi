# 0035 · OpenAI-compatible endpoints run on plain fetch behind an internal provider layer

## Status

Accepted (spike and issue #182, 2026-10-03; the owner chose plain `fetch` and config-only local models, confirmed 2026-10-04).

## Context

The native harness spoke only the Anthropic Messages API (ADR 0022), so there were no `local` targets, the router's local pricing (DESIGN §8.3) had nothing to price, and M4's "chores run on local or cheap targets" couldn't happen. One API format, OpenAI Chat Completions, covers Ollama, LM Studio, vLLM and OpenRouter. ADR 0022 deferred an internal provider interface until a second provider needed one. DESIGN §9.5 named the `openai` SDK for this format; whether to use it or plain `fetch` needed code, not reading.

The spike ran `openai` 7.19.0 (the newest version at least 14 days old) and a hand-written client against the same scripted endpoint: OpenRouter-shaped replies (reasoning text, `reasoning_details` streamed one piece per chunk, a tool call split across chunks, a usage chunk) and Ollama-shaped ones (a whole tool call in one chunk, a `reasoning` field).

What it showed:
- Both stream text and assemble split tool calls and usage. The SDK keeps unknown delta fields, aborts in about 3 ms with `APIUserAbortError`, retries a 429 on its own, and raises typed errors for an error sent mid-stream and a stream cut short.
- The SDK's `stream()` helper keeps only the last piece of `reasoning_details` streamed across chunks: the text and format of an OpenRouter reasoning block are lost, and the block can't go back to the model whole. Using the SDK would still mean iterating raw chunks and accumulating them ourselves, which leaves it only SSE parsing, retries and typed errors.
- The SDK reads `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID` and `OPENAI_LOG` unless each is passed explicitly, and always merges `OPENAI_CUSTOM_HEADERS` from the environment into every request, with no option to turn that off. It rejects an empty key, which Ollama needs none of, and sends `x-stainless-os`, `-arch` and `-runtime` headers to every endpoint, OpenRouter included.
- It is 18 MB unpacked, and releases almost daily, so the 14-day age rule keeps it well behind.

## Decision

1. **Plain `fetch`, no new dependency** (the owner's choice after the spike). `chat-completions.ts` is about 340 lines: an SSE reader that skips comments, an accumulator that keeps every field an endpoint sends, retries of 408, 409, 429 and 5xx twice before the reply starts (honouring `retry-after`, else 0.5 s doubling), and errors that name the endpoint and the fix. It reads nothing from the environment and sends only `content-type` and, when there's a key, `authorization`.
2. **An internal provider layer in `packages/harness-native`.** A `Provider` (`provider.ts`) has an `id` (the catalog's `provider`), `send` (stream one request from the session's prefix and transcript, yielding text deltas and returning the whole reply as blocks, a stop reason and tokens), `classify` (what an error says about the provider's health), `fix` (what a turn that ends on one names besides another route, e.g. how to replace a rejected key) and `failure` (its other errors as the user reads them). The Anthropic call moved into `anthropic.ts` with the same request bytes, effort messages and beta header included, so ADR 0022's tests (`adapter.test.ts`) pass unchanged. The adapter picks the provider by the route's model, through its catalog, and keeps everything else: the loop, tools, steers, limits, the cache check and `provider.failed`.
3. **Normalized blocks are the Messages API's shapes.** The transcript keeps text, image, tool use, tool result and thinking blocks as the Messages API spells them, which is what v1 transcripts on disk already hold, so none needs upgrading, plus one `carried` block: `{ type: "carried", provider, value }`, the fields a provider sent besides text and tool calls (`reasoning`, `reasoning_content`, `reasoning_details`), kept unchanged. Each provider sends only what it can read back: Anthropic drops carried blocks, and a Chat Completions endpoint drops thinking blocks and every other endpoint's carried blocks. A message left empty is skipped, and user messages in a row are joined, so a session can move between providers (an escalation from a local model to Sonnet) and back.
4. **Chat Completions mapping.** The session's system blocks become one `system` message and its tools become `function` tools, built the same way on every request. An assistant message carries its text, its `tool_calls` (arguments as JSON) and its carried fields back together. A user message's tool results become `tool` messages ahead of its text and images (images as base64 data URLs). Requests stream with `stream_options.include_usage`. No `max_tokens` is sent, since endpoints cap output differently and some refuse a cap above their own; `finish_reason` `length` ends the turn saying the output limit was hit. Effort goes as `reasoning_effort` when the model's catalog entry lists efforts, always the route's: it is a request parameter, so changing it mid-session would break the cache on servers that key on it (gpt-oss puts it in its system prompt; OpenRouter maps it onto an Anthropic model's thinking budget). Effort messages (ADR 0022's per-turn effort) stay behind, and auto effort leaves endpoint models alone (`decideTurnEffort`). Usage maps `prompt_tokens` less `cached_tokens` to input and `cached_tokens` to cache reads; there are no cache writes. Tool arguments that aren't a JSON object become `{}`, and the tool's own error says what's missing.
5. **The cache check is per provider.** Each provider fingerprints its own request (Chat Completions: the system message, the tools, one hash per message, model and `reasoning_effort`), and a request is compared with the session's last one to the same provider, since each provider keeps its own cache. Moving to another provider is a route change, which the switch-cost gate already prices. Tool search for many MCP tools (ADR 0031) is per provider too: a session that opens on an endpoint takes Verdandi's bridge, whose three tools any provider takes later, and one that opened on the Anthropic API's server search and moves onto an endpoint is sent its deferred tools in full, without the search tool or its blocks, the same on every request there, so its cache holds; refusing the move instead would strand the session on a provider that may be failing.
6. **Provider failures.** An endpoint's errors carry their HTTP status and `retry-after`, and map onto the same closed set of reasons as the Anthropic API's (`statusFailure` and `failureOf` in `provider-failure.ts`): 401 `auth`, 402 `billing`, 404 `model_not_found`, 408 and 504 `timeout`, 413 or a 400 about the context length `context_overflow`, 429 `rate_limit`, other 5xx `server_error`. Rate limits and missing models name the model. Past its retries a classified failure raises `provider.failed`, so routing around a failing endpoint (DESIGN §9.5) works as it does for Anthropic. An endpoint that can't be reached, a 403, a refused request or a stream cut short fail the turn naming the endpoint, its URL and the fix, as an unreachable Anthropic API does.
7. **`providers.yaml` in the Verdandi home**, read when verdandid starts. `endpoints` maps a name (lowercase, the catalog's `provider`, never `anthropic`) to `url`, `access` (`local` or `metered`) and `models`, each a model name mapped to `tier`, `context`, and optionally `vision` (default false), `efforts` (default none) and `price` in $/MTok (`input`, `output`, `cacheRead` and `cacheWrite` default to `input`). A metered model needs a price; a local one costs nothing unless priced. A model name must be unique across the native harness. A broken file stops verdandid, naming the file and the key. `verdandi routing replay` reads its models too (keys or not), so a policy that names one replays. Ships with no endpoints and no built-in local models: which local models to target first (DESIGN §23, question 6) is the owner's call, and they chose config only. The built-in policy doesn't route to local until one has been measured on the batch eval set.
8. **Keys.** A provider's key is `VERDANDI_<NAME>_API_KEY` (dashes as underscores), else the OS keychain's `verdandi` / `<name>-api-key`, which `verdandi key set <name>` fills; the Anthropic key is the same scheme's `anthropic`. A metered endpoint with no key stays off, and `verdandi start` says why; a local one runs without one. A key that's empty or holds whitespace stops startup, naming where it is. A key never travels in the clear: an endpoint that would send one (every metered endpoint, and any other a key is found for) must be on `https:` or on this machine (localhost, 127.0.0.0/8, ::1), or reading `providers.yaml` fails naming the endpoint's `url` and the fix; a keyless local server may use plain http, on the LAN too. Every `VERDANDI_*_API_KEY` leaves verdandid's environment once read and never reaches a process it starts (`isSecretVariable`).
9. **Catalog.** `HarnessAdapter` gains an optional `catalog`: the models a harness serves beyond the built-in catalog. The native adapter's holds the Anthropic models when it has a key and each running endpoint's models, and `catalogFor` adds it while native runs. The native harness runs when it has either.
10. **`local` usage.** The usage contract's `accessMode` gains `local` (widening a literal union keeps every stored event readable). A local turn's usage costs nothing and counts toward neither metered nor subscription spend; the spend dashboard labels it `local`; a trajectory is `local` when none of its turn's usage was metered or subscription.
11. **Tests.** `makeFakeChatCompletions` in `packages/testkit` streams scripted replies as real Chat Completions SSE through an injected `fetch`, the way `makeFakeAnthropic` does.

## Consequences

- Ollama's OpenAI-compatible API ignores the request's context size and runs every model at its own default `num_ctx`, which is far below most models' trained context. Set `OLLAMA_CONTEXT_LENGTH` (or the model's `num_ctx`) to at least the `context` given in `providers.yaml`, or long sessions get silently truncated.
- Auto effort (DESIGN §8.7) runs only on the Anthropic API's models; an endpoint model's turns all run at the route's effort.
- An unreachable endpoint isn't a provider failure, as an unreachable Anthropic API isn't: a stopped Ollama fails the turn naming the fix rather than routing around it.
- Not yet: OpenRouter's own `cost` and provider routing preferences, the Responses API, Gemini (§9.5's third format), `keyCommand`, rotating keys, per-endpoint concurrency limits, and recording which provider a trajectory ran on (a native turn's trajectory still names `anthropic` as its provider).
- A thinking block from Anthropic is lost to an endpoint the session moves to, and an endpoint's reasoning is lost to Anthropic; each still gets the other's text and tool calls.
